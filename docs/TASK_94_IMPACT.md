# 작업 94 영향 분석 및 구현 제안

작성일: 2026-11-17 · 담당: `songduckjin` · 대상: PR #24 (`task/94-character-selection`)

## 확인한 현행 구조

- 계정 하나에 캐릭터 세이브 하나가 연결된다. `djrpg_accounts.save_json`은 단일 `Save(version: 1)`이고 계정별 리비전·저장 요청 중복 제거도 하나씩이다 (`server/database.mjs`, `api/account.mjs`).
- 로그인/신규 가입/게스트 시작은 곧바로 그 세이브를 반환한다. 신규 가입 화면의 남성/여성 전사 선택은 계정 생성 절차이며, 별도 캐릭터 선택·생성 화면은 없다 (`src/ui/login.ts`). 저장 형식에 직업 필드는 없고 현재 UI의 직업 표기는 전사로 고정되어 있다 (`src/game/store.ts`, `src/ui/modals/accountModal.ts`).
- 부팅 시 하나의 세이브로 `World`, `Interface`, `SaveSync`를 만들고, 로컬 레거시 세이브 이전·오프라인 보상·자동 저장을 수행한다 (`src/main.ts`). 캐릭터를 바꾸는 단순 UI 조작만으로는 이 객체들을 안전하게 교체할 수 없다.
- 거래소는 게임 전체 매물과 계정별 내 거래·배달함을 제공하고, 아이템 소유권은 계정 ID 기준이다. 아이템 조회에는 `djrpg_accounts.save_json`의 가방·장비 JSON 경로가 쓰이고, 거래 결과도 현재 세이브에 적용된다 (`server/database.mjs`, `server/market.mjs`, `src/game/sync.ts`). 공용창고는 현재 없다.
- 공개 작업 현황에서 작업 94만 진행 중이다. 작업 90·91은 완료, 작업 92는 별도 담당자의 완료 작업이다. 열린 PR #20·#23의 내용은 이번 브랜치에 반영하거나 수정하지 않는다. PR #23의 API 키·GitHub Actions 작업은 중단 요청 상태다.

## 제안하는 데이터·화면 모델

1. **슬롯 정책:** 우선 무료 슬롯 3개만 제공한다. 최대 슬롯 수는 서버 설정으로 관리할 수 있게 하고, 3개 초과가 허용될 때만 3개 단위 페이지·좌우 버튼·스와이프를 활성화한다. 유료/무제한 확장은 가정하지 않는다.
2. **저장 경계:** 계정은 인증 주체로 유지하고, 계정 아래 슬롯 번호·고유 캐릭터 ID·개별 진행 세이브·수정 시각·리비전을 가진 캐릭터 레코드를 둔다. 레벨·경험치·층·가방·장비·도감·스킬·설정·오프라인 시간은 캐릭터별로 묶는다. **골드는 계정 레코드에 한 번만 저장**한다. 현재 `Save(version: 1)`의 `gold`와 `accountId`는 데이터 계약이므로 서버/클라이언트 전환 시 일관되게 바꾸고, 각 캐릭터가 독립된 골드 값을 갖지 않도록 한다. 캐릭터 ID는 요청과 DB 소유권 검사에 별도로 사용한다.
3. **선택·생성 흐름:** 로그인 후 슬롯 요약(실제 이름·성별·전사·레벨·층)을 받아 첫 3개를 표시한다. 선택된 슬롯을 강조한다. 빈 슬롯을 누르면 이름과 기존 지원 범위인 남/여 전사만 고르는 생성 화면으로 간다. 서버가 빈 슬롯·중복 이름 정책·상한을 검증하고 한 트랜잭션에서 생성한다. 선택/생성 후 해당 세이브를 불러와 게임을 시작한다.
4. **전환 안전성:** 전환 전에 자동 저장과 진행 중 거래를 완료·확인한다. 실패/충돌 시 전환을 취소하고 원인을 표시한다. 성공 시 기존 게임 루프를 정리하고 선택 캐릭터로 재부팅한다. 다른 탭의 동시 변경은 캐릭터별 리비전으로 차단한다.
5. **공용 골드·창고·거래소:** 서버의 계정 단위 골드 잔액을 모든 캐릭터에 동일하게 보여주고 거래·창고 요청과 원자적으로 갱신한다. 공용창고는 별도 계정 자산으로 두며, 넣기/꺼내기는 캐릭터 가방·아이템 소유 위치를 같은 트랜잭션에서 바꾼다. 기존 거래소의 전체 매물 공개 및 계정별 내 거래·배달함 범위는 유지한다. 매물·배달 금화는 계정 잔액에, 아이템은 요청 캐릭터 가방 또는 공용창고 정책에 따라 반영한다. 아이템 소유 레코드에 캐릭터/창고 위치를 구분하여 다른 슬롯의 아이템을 세이브에 끼워 넣는 요청을 거절한다. 캐릭터 전환 중 거래·창고 요청과 미확인 응답 재시도는 잠근다. 캐릭터 삭제/슬롯 재사용 기능은 이번 범위에서 제공하지 않는다.

## 비파괴 이전·호환성·롤백

1. 배포 전 계정 세이브와 거래·아이템 테이블을 백업하고, 백업 사본의 행 수·무결성과 기존 세이브의 슬롯 1 읽기 경로를 검증한다. 사용자의 2026-11-17 지시에 따라 별도 복원 모의 검사는 완료 기준에서 제외한다.
2. DB 스키마는 추가 방식으로 적용한다. 계정별 첫 접근 시 트랜잭션에서 기존 `save_json`을 슬롯 1로 **그대로 백업/이전**하고 기존 `gold`를 계정 공용 잔액으로 한 번만 추출한다. 다시 실행해도 중복 생성·골드 중복 지급이 없게 고유 키와 이전 표식을 둔다. 원본 `djrpg_accounts.save_json`은 보존한다. 레거시 로컬 세이브 이전도 슬롯 1에만 적용하고 서버 저장 성공 후에만 로컬 원본을 삭제한다.
3. 새 API는 캐릭터 ID/슬롯과 리비전을 명시적으로 받아 계정 소유 여부를 서버에서 검증한다. 기존 클라이언트의 캐릭터 ID 없는 저장은 전환 기간에 슬롯 1로만 제한하거나 명시 오류로 갱신을 요구한다. 어느 방식을 쓰든 오래된 클라이언트가 새 슬롯의 진행 상황을 덮어쓰지 못해야 한다.
4. `djrpg_accounts.save_json`을 참조하는 거래소 쿼리와 아이템 정합성 검사를 캐릭터 저장소·공용창고 기준으로 함께 바꾼 뒤 전환한다. 기존 아이템 소유 정보는 슬롯 1로 귀속하고, 다른 슬롯/창고에 복제되지 않았는지 검증한다. 계정 공용 골드는 저장·거래·창고 동시 요청에서 서버 트랜잭션과 리비전으로 직렬화한다.
5. 장애 시 UI/새 API를 비활성화해 신규 슬롯 쓰기를 멈추고 백업 및 캐릭터 레코드로 복구한다. **기존 단일 세이브 코드로 단순 재배포하는 롤백은 신규 슬롯 진행을 잃을 수 있으므로 금지**한다. 필요하면 슬롯별 데이터 내보내기·복원 경로를 먼저 준비한다.

## 승인 전 결정 및 구현 순서

- **필수 승인:** 위 계정/세이브/API/거래/공용창고 계약 변경, 슬롯 1 비파괴 이전, 구형 클라이언트 처리 방식을 승인받아야 한다. 작업지시서가 이 단계의 명시 승인을 요구한다.
- **제품 결정:** 초기 최대 슬롯을 3개로 고정할지, 3개 초과를 처음부터 허용할지 정해야 한다. 제안은 초기 3개다. 생성 이름은 기존 계정 이름과 별개로 둘지 결정해야 한다. 제안은 슬롯별 이름, 기존 슬롯 1 이름 유지다.
- 승인 후 순서: 저장/마이그레이션·소유권 테스트 → API/동기화·거래 회귀 테스트 → UI → `pnpm run check`, `pnpm test`, `pnpm run build`, `git diff --check` → 작업 상태·개인 기록 갱신. main 직접 수정·자동 병합은 하지 않는다.

이 문서는 승인 전 영향 분석으로 시작했다. 작업 90·91·92의 상태는 변경하지 않았다.
