## 1. 작업 목적

현재 DJRPG 프로젝트의 모듈 구조와 의존 관계를 분석하여, 기능 간 책임 침범과 과도한 결합을 파악한다. 두 명의 개발자가 서로의 작업을 불필요하게 수정하지 않고 독립적으로 개발할 수 있도록 모듈 경계, 데이터 소유권, 공개 인터페이스 및 단계별 개선안을 제안한다.

## 2. 수행 범위

1. 프로젝트 디렉터리와 주요 모듈의 역할을 조사한다.
2. 실제 import 및 호출 관계를 바탕으로 의존성 그래프를 작성한다.
3. 순환 참조, 과도한 결합, 책임이 집중된 파일과 공통 상태 직접 변경 지점을 식별한다.
4. 전투, 아이템·인벤토리, 성장·보상, 계정·세이브·동기화, 거래소, UI·렌더링 영역의 책임과 의존 방향을 분석한다.
5. 두 작업자의 독립 개발을 방해하는 공유 파일·데이터 계약·상태 의존성을 정리한다.
6. 목표 디렉터리 구조, 모듈별 책임, 공개 인터페이스, 데이터 소유권 및 의존성 규칙을 제안한다.
7. 우선순위와 영향 범위, 회귀 위험, 테스트 및 세이브 호환성 검증을 포함한 단계별 리팩토링 계획을 작성한다.

## 3. 작업 제한

- 사용자가 구체적인 착수 지시를 내리기 전까지 진단을 시작하지 않는다.
- 진단 단계에서는 `src/`, `api/`, `server/`, `tests/`의 실행 코드 및 기존 게임 동작을 수정하지 않는다.
- 세이브 데이터 형식, API 계약, DB 스키마를 변경하지 않는다.
- `docs/DESIGN.md`의 기획 내용을 별도 지시 없이 구현 요구사항으로 간주하지 않는다.
- 실제 구조 변경은 진단 결과를 공유하고 사용자 승인을 받은 뒤 별도 작업으로 등록한다.
- 작업 중 공통 영역 변경이 필요해 보이면 임의로 수정하지 말고 영향 범위와 승인 필요 사항을 먼저 보고한다.

## 4. 산출물

진단 결과 문서에 다음 내용을 포함한다.

- 현재 모듈 구조 및 의존성 요약
- 순환 참조와 결합도가 높은 영역 목록
- 모듈별 책임 및 책임 침범 사례
- 공유 데이터·상태의 소유권과 계약
- 독립 개발을 위한 권장 모듈 경계 및 목표 구조도
- 단계별 리팩토링 로드맵과 우선순위
- 기능, 세이브, API, DB 호환성 위험 및 검증 계획

## 5. 완료 기준

- 분석 내용이 실제 소스 코드의 import·호출 관계를 근거로 한다.
- 문제 영역마다 영향받는 모듈과 위험을 명시한다.
- 두 작업자가 분리해서 진행할 수 있는 업무 경계와 공통 변경 승인 기준을 제안한다.
- 목표 구조와 단계별 이행 계획이 제시되어 있다.
- 진단 단계에서 실행 코드나 데이터 계약이 변경되지 않았다.
