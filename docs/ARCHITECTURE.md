# DJRPG 아키텍처 및 구조 개선 로드맵

## 프로젝트 구조와 계층
- `src/ui`: 화면·입력·모달. 게임 규칙을 직접 소유하지 않고 `src/game` 모듈을 소비한다.
- `src/game`: 도메인 규칙·전투·진행·세이브 동기화.
- `src/game/sync.ts`: 클라이언트와 API 사이의 저장·요청 경계.
- `/api`·`functions/api`: 배포 플랫폼별 어댑터. 실제 계약과 처리는 `server/endpoints`·`server/*`에서 공유한다.
- 계층 방향은 `src/ui` → `src/game` → `src/game/sync.ts` → API 어댑터 → `server/*`다. 예외는 `sync.ts`에서 `ui/login.ts`를 참조하는 로그인 복구 연결 하나。

## 단일 책임 분리 원칙
- 기능 수정·리팩터링 때 쪼갤 수 있는 규칙은 순수 도메인 모듈로 분리한다.
- 판정·상수는 한 곳에만 둔다. UI는 판정 결과를 소비하고, 서버 검증은 같은 계약을 독립적으로 확인한다.
- 한 PR은 한 도메인으로 제한한다. 공용 계약·`store.ts`·`database.mjs`를 건드리면 PR 본문에 영향과 호환성 근거를 적고 관련 매뉴얼을 갱신한다.

## 구조 개선 로드맵
순서대로, 각각 별도 PR로 진행한다。

1. **전투 코어 통합** — 필드(`world.ts`)·던전(`dungeonBattle.ts`)·방치(`offline.ts`)가 공유하는 피해·사거리·스폰·드롭 규칙을 `src/game/combat/` 순수 모듈로 모은다. 두 전투 구현은 공통 코어를 소비하고 서버 리플레이는 코어만 import한다.
2. **폴링·통신 분리** — 월드보스·전광판·여정·유지보수 폴링을 공용 스케줄러(후보 `src/game/polling.ts`)로 모은다. 숨은 탭 정지·캐시·요청 예산을 한 곳에서 관리한다.
3. **세이브 인벤토리 정규화** — `save_json`의 `bag`·`equipment`를 `djrpg_items` 계열 정규화 테이블로 이관한다. `reconcileItems`를 해당 테이블 기준으로 전환하고, 마이그레이션·롤백 계획과 호환성 검증을 필수로 한다.
