# 작업 209 — 100명 동시 접속 대응

기존 구조(Cloudflare Pages Functions + Turso/libSQL)를 그대로 두고, **서버가 신뢰하는 경계**와 **요청 수·잠금 경합**을 정리했습니다. 저장 형식·API·에러 코드(`401 SESSION_REPLACED`, `409 SAVE_CONFLICT`/`ITEM_CONFLICT`/`CHARACTER_CONFLICT`, `426 VERSION_OUTDATED`)는 그대로입니다.

설계·실측·남은 위험은 **`docs/SCALE_100.md`** 에 정리했습니다.

## 1) 이미 해결되어 있어 바꾸지 않은 것

| 영역 | main의 구현 |
|---|---|
| 아이템 복제·소유권·스탯 변조 | `reconcileItems` + `djrpg_item_owners`/`djrpg_character_item_owners`, `identity` 대조 → 409 `ITEM_CONFLICT` |
| 저장·거래·창고 멱등 | `djrpg_save_requests`·`djrpg_market_requests`·`djrpg_warehouse_requests` + `sync.ts`의 동일 requestId 재전송 |
| 거래소 경합 | `mutate` 한 트랜잭션에서 매물 재조회 후 `state='active'` 조건 커밋 |
| 월드보스 | 서버 `replayBoss` 피해 재계산, 공유 HP 원자 차감, `djrpg_boss_rewards` PK로 중복 보상 차단 |
| DB 초기화·연결 | `schema()`/`worldBossSchema()`/`dungeonSchema()` Promise 캐시, `market-connection.mjs` 연결 재사용 |
| 던전 순위 근거 | 클라이언트 입력이 아니라 서버 세이브에서 층을 읽음 |

## 2) 실제 코드 변경 (우선순위별)

**① 서버 검증 경계** — `server/save-guard.mjs`(신규)
- 마지막 저장 이후 **서버 시계로 흐른 시간**(최대 12시간)과 층·직업 규칙으로 상한을 계산해 **넘친 값만** 잘라 냅니다(거부하지 않아 정상 보상이 사라지지 않습니다). 응답에 `clamped`가 실리고 로그에 개수가 남습니다.
- 킬 `60+6/초`, 보스 `ceil(킬/30)+1`, `playSeconds` `경과+5`, `maxFloor` `+보스`, 레벨/경험치는 `expToNext`로 시뮬레이션, 금화 `(킬×(3+층)+보스×70×층)×2+1000`, 강화석, 스킬포인트.
- 거래소 판매대금·우편 보상처럼 **서버가 같은 트랜잭션에서 주는 몫**은 `writeSave(..., {goldCredit})`로 상한에 더합니다(`market.mjs`, `journey.mjs`).
- 새로 만들어지는 아이템만 개수(`8+0.5/초`)·능력치(`rollItem` 공식 ×2.5) 상한 검사를 합니다. **이미 저장돼 있던 아이템은 소유 기록만 채웁니다** — 첫 배포에서 기존 가방이 거부되지 않게.
- 오프라인 보상은 클라이언트 계산을 유지하되, 위 상한(경과 시간 기준)으로 서버가 검증합니다.

**② 던전 최고층 서버 검증** — `server/dungeon-verify.mjs`(신규)·`server/dungeon.mjs`
- `DungeonBattle`이 DOM 없는 순수 로직이라 서버가 그대로 리플레이해 "이 세이브로 그 층을 깰 수 있는지 / 최소 클리어 시간"을 계산합니다.
- `start`(서버가 시작 시각 기록) → `submit`(기록+1층·시작 기록·최소 시간[리플레이의 절반, 최소 10초/미클리어 30초] 확인) → 그때만 `djrpg_dungeon_records`를 올립니다.
- `writeSave`는 세이브의 `dungeonFloor`를 **검증된 기록+1까지만** 저장합니다. `list`는 읽기 배치만 씁니다.
- 클라이언트: `dungeonField.ts` 층 진입에서 `live.enter(floor)`, 결과에서 `live.submit(floor)`, 검증 실패 시 서버 시계를 기다렸다 최대 3회 재전송.

**③ 저장 요청 최소화** — `src/game/sync.ts`·`src/main.ts`
- `dirty`/`changeSeq`/`lastSaveAt` 도입. `queueSave`는 마지막 저장 5초 뒤로 예약(예전 1초 디바운스), 5초 점검은 `flushIfDirty()` — **변경이 없으면 요청 0건**. 저장 중 변경은 `changeSeq` 비교로 이어서 보냅니다.
- `flush()` 자체는 종전대로 항상 저장합니다(명시 저장 계약 유지).

**④ 월드보스 읽기/쓰기 분리** — `server/world-boss.mjs`
- `action:'list'`는 계정·오늘 row·내 도전 수·순위·정산 필요 여부를 **읽기 배치 한 번**으로 확인하고, 정산할 것이 없으면 쓰기 트랜잭션 없이 답합니다. 오늘 첫 요청·정산 필요 시에만 종전 쓰기 경로.

**⑤ 연결 재사용·계측** — `server/connection.mjs`·`server/metrics.mjs`(신규)
- account/dungeon/world-boss도 거래소처럼 초기화된 연결을 재사용(`createDbClient` 주입 경로는 그대로).
- `Server-Timing`(`schema`/`db`/`tx`/`replay`/`settle`/`total`)과 구조화 로그 한 줄(`{"event":"api",...}`). **세이브 본문·토큰·접속 문자열은 남기지 않습니다.**

**⑥ 거래소 검색** — `scripts/explain-market-query.mjs`(신규)
- 2만 건: 모든 조회가 인덱스를 타고(SCAN 없음) 기본 0.8ms·이름 0.6ms·가격 정렬 15ms·스탯 정렬 15ms. 10만 건 스탯 정렬 73ms.
- 100명 규모에서 병목이 아니라고 판단해 **인덱스·페이지네이션을 바꾸지 않았고 실측 근거만 남겼습니다.**

## 4) 남은 위험

- 운영 p95는 측정하지 않았습니다(배포 후 `Server-Timing`·Turso 대시보드로 확인 필요).
- 던전 검증은 시간 기반 **가능성 경계**입니다 — 클리어하지 않고 그 시간만큼 기다렸다 제출하는 스크립트는 막지 못합니다.
- 능력치 상한의 2.5배 여유 안에서는 정상 최대치 아이템 1개 생성은 가능합니다(대량 생성은 개수 상한이 막습니다).
- 거래소 스탯 정렬은 활성 매물 10만 건 규모에서 70ms대입니다.
