# 100명 동시 접속 대응 설계 (작업 209)

DJRPG는 Cloudflare Pages Functions + Turso(libSQL) 위에서 돈다. 이 문서는 **100명 동시 접속**을 목표로
현재 `main`을 전수 확인해 ① 이미 해결돼 있던 것(중복 수정 금지) ② 실제 빈틈 ③ 이번에 추가한 경계와 계측
④ 실측 결과 ⑤ 남은 위험을 기록한다. 코드 계약은 `docs/CODE_MAP.md`, 수정 레시피는 `docs/QUICK_PATCH.md` §1.

## 1. 이미 해결되어 있어 바꾸지 않은 것

| 영역 | main의 구현 | 확인한 계약 |
|---|---|---|
| 아이템 복제·소유권·스탯 변조 | `reconcileItems` + `djrpg_item_owners`/`djrpg_character_item_owners`, `identity(item)` 대조 | 409 `ITEM_CONFLICT`, 캐릭터 슬롯 소유까지 확인 |
| 저장 멱등·재시도 | `djrpg_save_requests`(requestId→revision), `sync.ts` `pendingSave` 동일 requestId 재전송 | 재전송은 같은 revision, 새 변경은 새 요청 |
| 거래·창고 멱등 | `djrpg_market_requests`·`djrpg_warehouse_requests`, `sync.mutate`/`transferWarehouse`의 단일 요청 | 같은 requestId는 한 번만 |
| 거래소 경합 | `mutate` 한 트랜잭션 안에서 매물 재조회 → `state='active'` 조건 커밋 | 두 번째 구매는 `NOT_AVAILABLE` |
| 월드보스 피해량 | `replayBoss`가 서버에서 전투를 다시 계산(클라이언트 피해량 무시), 공유 HP는 쓰기 트랜잭션 `hp=hp-?` | 위조 피해 무시, 중복 보상은 `djrpg_boss_rewards` PK |
| 던전 순위 근거 | `dungeon.mjs`가 클라이언트 입력이 아니라 서버 세이브에서 층을 읽음 | 층은 단조 증가 |
| DB 연결·스키마 초기화 | `schema()`·`worldBossSchema()`·`dungeonSchema()`가 Promise 캐시, `market-connection.mjs`가 연결 재사용 | 요청마다 DDL 반복 없음 |
| 저장 충돌 안내 | `sync.handleError`의 `SAVE_CONFLICT` 오버레이, `ITEM/CONFLICT` 재로드 + 10초 루프 차단, 426 처리 | 오류 코드 유지 |

## 2. 실제 빈틈 (이번에 닫은 것)

1. **골드·경험치·레벨·처치 수·도달 층이 전적으로 클라이언트 신뢰** — 서버는 `gold 0~9e12` 형식만 봤다.
   세이브 한 번으로 금화 1e12를 만들 수 있었다.
2. **새 아이템 id는 검증 없이 등록** — 소유 기록이 없는 id는 능력치를 무엇으로 보내든 `djrpg_item_owners`에
   `inventory`로 들어갔다(기존 아이템의 스탯 변조만 막혀 있었다).
3. **오프라인 보상 무검증** — `src/game/offline.ts`가 클라이언트에서 계산해 세이브에 더한다.
4. **던전 최고층** — 서버는 "낮아지지 않게"만 강제해서, 세이브에 `dungeonFloor: 10`을 쓰면 그대로 통과했다.
5. **변경이 없어도 5초마다 저장** — `src/main.ts`의 `setInterval(flush, 5000)`.
6. **월드보스 조회가 쓰기 트랜잭션** — `action:'list'`도 오늘 row INSERT·만료 도전 정산을 하며 쓰기 잠금을 잡았다.
7. **요청마다 새 DB 클라이언트** — account/dungeon/world-boss 엔드포인트가 매 요청 `client(env)`+`close()`.
8. **계측 없음** — 어느 단계가 느린지, 클램프가 얼마나 일어나는지 알 수 없었다.

## 3. 서버 검증 경계 (`server/save-guard.mjs`)

저장은 **거부하지 않고 상한만 적용**한다(정상 보상이 사라지지 않게, 에러 코드·응답 형식 불변).
상한의 근거는 서버가 아는 두 가지다: **마지막 저장 이후 서버 시계로 흐른 시간**(`character_updated_at`,
최대 12시간)과 **층·직업 규칙**(킬당 금화·경험치, 층 클리어 킬 수, 드롭 공식).

| 필드 | 상한 | 근거 |
|---|---|---|
| `kills` | `이전 + 60 + 6×경과초` | 스폰 간격 ≥0.55초·18마리 상한(정상 초당 2마리 안팎) |
| `bossKills` | `이전 + ceil(킬상한/30)+1` | 보스는 120마리마다 |
| `playSeconds` | `이전 + 경과초 + 5` | 서버 시계 |
| `maxFloor` | `이전 + 보스상한` | 층은 보스 처치로만 오른다 |
| `level`/`exp` | 경험치 상한(`킬상한×45×2`)을 성장식에 넣어 계산한 결과 | `expToNext` |
| `gold` | `이전 + (킬상한×(3+층) + 보스×70×층)×2 + 1000 + 서버지급분` | 킬 보상 공식 |
| `stones` | `이전 + ceil(킬상한×0.2)+5 + 서버지급분` | 분해 최대 5개/장비 |
| `skillPoints` | `레벨-1-투자한 스킬 랭크` | 레벨업 지급 |
| 새 아이템 개수 | `8 + ceil(경과초×0.5)` | 정상 드롭 78층 초당 0.07개 |
| 새 아이템 능력치 | `rollItem` 공식 상한 ×2.5(옛 공식 여유) | `baseItems` 티어 × 등급배율 × plus |
| `dungeonFloor` | 검증된 기록+1 | 아래 §4 |

- **서버가 같은 트랜잭션에서 정당하게 더해 주는 몫**은 `writeSave(..., { goldCredit, stoneCredit })`로 넘긴다:
  거래소 판매대금 수령(`market.mjs`), 우편·업적 보상 수령(`journey.mjs`).
- **이미 저장돼 있던 아이템**은 소유 기록만 채우고 능력치 검사를 건너뛴다 — 그러지 않으면 이 경계를 처음
  배포한 날 기존 계정의 가방이 통째로 거부된다(첫 배포 안전).
- 클램프가 일어나면 응답에 `clamped: ['gold', ...]`가 실리고 구조화 로그에 `clamped` 개수가 남는다.

## 4. 던전 클리어 서버 검증 (`server/dungeon-verify.mjs`·`server/dungeon.mjs`)

던전 전투 `src/ui/dungeonBattle.ts`의 `DungeonBattle`은 DOM을 쓰지 않는 순수 로직이라 **서버가 그대로
리플레이**할 수 있다(월드보스 `replayBoss`와 같은 방식). 그래서 "이 세이브로 이 층을 깰 수 있는가"와
"가장 빠른 클리어 시간"을 서버가 계산한다.

1. 클라이언트가 층에 들어가면 `POST /api/dungeon {action:'start', floor}` → 서버가 그 층의 시작 시각을 적는다
   (`djrpg_dungeon_attempts`, 같은 층을 다시 열면 기존 시각 유지).
2. 클리어하면 `{action:'submit'}` → 서버가 ① 세이브의 층이 기록+1인지 ② 시작 기록이 있는지
   ③ `started_at`부터 **리플레이 클리어 시간의 절반(최소 10초, 리플레이가 못 깨면 30초)**이 흘렀는지 확인하고,
   통과하면 `djrpg_dungeon_records`를 올린다.
3. `writeSave`는 세이브의 `dungeonFloor`를 **기록+1까지만** 저장한다 → 클라이언트가 세이브로 최고층을 올릴 수 없다.
4. 순위(`dungeon.mjs`)는 계정 세이브(≤ 기록+1)에서 층을 읽으므로 기록과 항상 일치한다.
5. **배포 이전 세이브 따라잡기**: 서버 기록이 비어 있는데 저장된 세이브가 이미 더 깊이 간 계정(순위·검증이
   없던 시절)은 `submit` 한 번으로 그 층을 그대로 인정한다. 그 뒤로는 한 층씩만 오른다. 이 예외가 없으면
   그 계정들은 영원히 순위에 오르지 못한다(새 계정은 저장 단계에서 기록+1로 잘려 여러 층을 뛸 수 없다).

`action:'list'`는 **읽기 배치 한 번**으로 답한다(쓰기 트랜잭션 없음).

클라이언트 변경은 두 곳뿐이다: `ui/dungeonField.ts`의 `resetBattle`·초기 진입에서 `live.enter(floor)`,
`game/dungeonLive.ts`의 `enter()`와 `submit(floor)`(검증 실패 시 서버 시계를 기다렸다 최대 3회 재전송).

## 5. 저장 요청 최소화 (`src/game/sync.ts`·`src/main.ts`)

- `markDirty()`/`changeSeq`로 "아직 못 보낸 변경"을 추적한다. `flush()`는 그대로 저장하지만,
  5초 점검(`setInterval`)은 `flushIfDirty()`를 불러 **변경이 없으면 요청을 만들지 않는다**.
- `queueSave()`는 마지막 저장에서 5초가 지난 시점까지 기다린다(1초 디바운스 → 최대 5초 간격).
  사냥 중에는 처치마다 변경이 생기므로, 예전에는 1초에 한 번 저장 요청이 나갔다.
- 저장 응답을 받은 뒤 `changeSeq`가 그대로면 dirty를 지우고, 바뀌었으면 즉시 다음 스냅샷을 보낸다
  (저장 중 변경 병합). 응답 유실은 같은 requestId로 재시도, 409/426/401 처리는 종전 그대로.

## 6. 월드보스 읽기/쓰기 분리 (`server/world-boss.mjs`)

`action:'list'`는 ① 계정·오늘 row·내 도전 수·순위 ② 정산이 필요한지(만료 도전·정산 안 된 날)를 **읽기 배치
한 번**으로 확인하고, 정산할 것이 없으면 그대로 답한다. 오늘 첫 요청이거나 정산이 필요할 때만 종전 쓰기
트랜잭션 경로로 내려간다. 피해량 재계산·공유 HP 원자성·중복 보상 방지는 그대로다.

## 7. 연결 재사용·계측

- `server/connection.mjs` `sharedConnection`: account/dungeon/world-boss도 거래소처럼 초기화된 연결을 재사용한다.
  `createDbClient`를 넘긴 호출(테스트·Vercel 어댑터)은 종전처럼 자기 연결을 쓰고 닫는다.
- `server/metrics.mjs`: `Server-Timing` 헤더(`schema`·`db`·`tx`·`replay`·`settle`·`total`)와 구조화 로그
  `{"event":"api", path, action, status, ms, dbMs, txMs, code, clamped}`. **세이브 본문·토큰·접속 문자열은 남기지 않는다.**
  월드보스는 `replayMs`·`settleMs`, 저장은 `clamped` 개수를 남긴다.

## 8. 실측 (격리 환경)

### 8.1 100명 부하 테스트 — `scripts/load-test-100.mjs`

임시 로컬 SQLite 파일 + 실제 엔드포인트 모듈, DB 연결 8개, 로컬 잠금은 재시도로 흡수.

| 시나리오 | 요청 | 오류 | p50 | p95 | p99 | 서버 처리 p95 |
|---|---|---|---|---|---|---|
| 100명 · 10초 · 저장 1초 주기 | 1,000 | 0 (0%) | 1.4ms | 2.0ms | 9.2ms | 1.6ms |
| 100명 · 6초 · 저장 100ms 주기 | 4,109 | 0 (0%) | 1.3ms | 1.8ms | 2.6ms | 1.6ms |
| 100명 · 6초 · 저장100ms + 거래소 조회 혼합 | 4,595 | 0 (0%) | 1.2ms | 1.5ms | 2.3ms | - |

**이 수치는 이 환경(로컬 파일 DB·한 프로세스)의 측정값이다.** 운영 Turso·Cloudflare의 p95가 아니며,
네트워크 왕복·콜드 스타트·동시 쓰기 대기열은 여기에 없다. 100명 처리 가능 여부의 근거로 쓰지 않는다.

### 8.2 거래소 실행 계획 — `scripts/explain-market-query.mjs`

20,000건(판매 완료 4,000): 모든 조회가 인덱스를 탄다(SCAN 없음).
기본 목록 0.8ms, 이름 검색 0.6ms, 내 매물 0.2ms, 시세 0.1ms. 가격 정렬 15ms, 스탯 필터 정렬 15ms
(`USE TEMP B-TREE FOR ORDER BY` — 판매 중 매물을 정렬).

100,000건: 기본 목록 0.9ms, 가격 정렬 30ms, **스탯 필터 정렬 73ms**.

→ 100명 규모에서는 병목이 아니라고 판단해 **인덱스·페이지네이션을 바꾸지 않았다**. 정렬 기준이
가격·스탯·최신순으로 여러 개라 인덱스 하나로 모두 덮을 수 없고, 지금 필요한 인덱스는 이미 있다.

## 9. 남은 위험

- **운영 p95는 측정하지 않았다.** 로컬 측정값으로 100명 처리 가능 여부를 단정하지 않는다. 실제 확인은
  배포 뒤 운영 `Server-Timing`·Turso 대시보드로 한다.
- **던전 최고층 검증은 "가능성 경계"**다. 서버 리플레이 시간의 절반만 요구하므로, 클리어를 실제로 하지 않고
  그 시간만큼 기다렸다 제출하는 클라이언트는 막지 못한다(자동화 스크립트 수준의 우회는 남는다).
- **능력치 상한의 2.5배 여유**는 옛 공식 세이브를 살리기 위한 값이다. 그 안에서는 정상 최대치 아이템을
  만들 수 있으므로, "완벽한 아이템 1개" 생성은 여전히 가능하다(대량 생성은 개수 상한이 막는다).
- **클램프된 클라이언트의 화면과 서버 값이 잠시 다를 수 있다.** 서버가 잘라 낸 값을 클라이언트에
  되돌려 주지 않으므로(응답의 `clamped`만 알린다), 조작된 클라이언트는 로컬 금화가 높은 채로 남는다.
  정상 플레이는 상한 아래라 영향이 없다.
- 거래소 스탯 정렬은 활성 매물이 10만 건 규모가 되면 70ms대다. 그때는 (state, json 스탯) 인덱스나
  검색 전용 테이블을 검토한다.
