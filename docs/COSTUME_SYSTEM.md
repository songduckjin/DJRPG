# DJRPG 캐릭터 외형·코스튬 시스템 정의

> 단일 기준 문서(Source of Truth). 프로토타입 전 설계 기준이며, 구현 상세는 실물 검증 후 추가한다.

## 1. 목표와 범위

플레이어 캐릭터의 본체, 장비, 무기 계열별 동작, 스킬 모션을 독립적으로 조합한다. 모든 장비에 모든 프레임을 반복 제작하지 않고 장비 성격에 따라 정지 이미지 부착(attach) 또는 프레임 이미지(frames)를 사용한다.

초기 적용 범위는 플레이어 전사 1명이다. 몬스터와 NPC는 현행 렌더링 구조를 유지한다. Save, 아이템 UUID·소유권·능력치, Turso DB 및 API 계약은 변경하지 않는다. 외형 ID는 기존 아이템 정보에서 런타임에 매핑하고 Save에 저장하지 않는다.

## 2. 현재 구현과 목표 구조 구분

현재 src/game/appearance.ts, src/game/render.ts, src/game/render/entities.ts는 통합 바디 시트와 무기 소켓 중심의 기존 구현이다. heroSockets.ts는 전사 남녀의 무기 위치를, gearTint.ts는 기존 갑옷·투구 팔레트 변형을 담당한다. 장비창 미리보기는 src/ui/equipmentPortrait.ts의 별도 경로다.

작업 135(PR #71)는 기존 통합 바디 시트의 4티어 갑옷·투구 팔레트 구분을 구현한 이력이다. 이는 현행 코드의 설명이지, 신규 코스튬 시스템에서 모든 장비를 통합 시트로 제작하라는 정책이 아니다.

신규 구조가 검증될 때까지 기존 필드 렌더링, 장비창 미리보기 및 에셋은 유지한다. 기존 리소스 삭제는 신규 시스템 전환과 참조 검사 이후 별도 작업으로만 한다.

작업 136 PR #72는 내 정보 UI 개편을 포함한 Draft PR이다. UI 레이아웃은 재사용 후보로 보존하되, 현재 초상화 구현이 최종 코스튬 렌더러 계약이라고 간주하지 않는다. 공용 외형 계획이 확정되면 미리보기 연결 방식을 다시 검토한다.

## 3. 기준 정책과 프로토타입 가설

| 항목 | 초기 기준 | 상태 |
|---|---|---|
| 방향 | 오른쪽 원본 + X축 좌우 반전, 2방향 | 기존 구조와 호환 |
| 시점 | 현재 DJRPG의 2.5D 필드에 맞는 측면 중심 2D 스프라이트 | 유지 |
| 본체 분리 | 머리 포함 몸통 / 양팔 / 다리의 3영역 | 프로토타입 기준 |
| 피벗 | 발바닥 접지점 중앙 | 프로토타입에서 보정 |
| 프레임 크기 | 고정 너비를 선결하지 않음. 가장 큰 동작을 포함하는 캔버스 사용 | 실측 후 확정 |
| 기본 동작 | 대기 1, 걷기 8, 기본 공격 4프레임을 초기값으로 사용 | 데이터로 관리 |
| 장비 방식 | 정지 장비는 attach, 실루엣 변형 장비는 frames | 슬롯별 검증 |
| 무기 계열 | 한 손 검과 대검을 먼저 비교 | 도끼·둔기는 후속 |
| 스킬 | 베기 / 회전 / 내려찍기 / 발동 자세의 4개 템플릿 | 새 템플릿은 근거가 있을 때만 추가 |
| 회전 스킬 | 평면 본체를 무리하게 360도 회전시키지 않고 회오리·잔상 등 이펙트 중심 | 전용 방향 아트 후순위 |
| 성별 | 공통 이미지 우선, 체형 적합성이 깨지는 부위만 성별 분리 | 대표 장비로 검증 |
| 몬스터·NPC | 현행 방식 유지 | 범위 제외 |

### 3.1 슬롯별 제작 방식 가설

| 슬롯 | 우선 방식 | 검증 기준 |
|---|---|---|
| 주무기·보조무기 | attach | 손 위치·회전·Z-order 데이터로 충분한지 |
| 투구 | attach | 머리 앵커와 가림이 자연스러운지 |
| 망토 | attach | 등 앵커 및 프레임별 앞뒤 순서가 충분한지 |
| 갑옷 몸통 | frames 검토 | 몸통 프레임과 무기 계열별 자세 차이를 재사용할 수 있는지 |
| 신발 | attach 우선, 필요 시 frames | 발 움직임에서 미끄러짐·겹침이 발생하는지 |
| 장갑 | attach 우선 | 팔·손 부착으로 충분한지 |

모든 장비에 모든 동작의 프레임을 제작하지 않는다. 같은 장비가 attach와 frames를 혼합해야 한다면 보조 레이어가 필요한지 먼저 확인한다.

### 3.2 무기 계열과 갑옷 프레임

본체 모션은 직업 × 성별 × 무기 계열 × 동작을 기준으로 찾는다. 한 손 검과 대검은 손 위치와 공격 자세가 다를 수 있다.

무기 계열별 본체 모션이 다르다고 해서 갑옷 이미지도 자동으로 복제하지 않는다. 같은 갑옷을 한 손 검과 대검 모션 위에 적용하고 실루엣이 깨지는 경우에만 별도 갑옷 프레임 세트를 추가한다.

### 3.3 스킬 모션 템플릿

스킬별 차이는 우선 무기 궤적, 재생 속도, 타격 시점 및 이펙트로 표현한다. 템플릿 추가는 본체와 frames 장비의 제작량을 늘리므로 기존 4종으로 표현할 수 없는 동작이 확인된 경우에만 검토한다.

실제 피해 판정과 이동은 게임 로직이 소유한다. 렌더러는 모션과 이펙트를 표시한다. 공격 속도에 따른 시각 재생 배율을 적용하더라도 전투 판정 규칙이나 월드 위치를 렌더러가 변경하지 않는다.

**v1.1 확정 기준:** v1.1에서 `src/game/skills.ts`의 액티브 스킬들을 4대 템플릿(`베기` / `회전` / `내려찍기` / `발동 자세`)에 매핑하는 표를 확정한다. 매핑 대상은 현재 `skills` 레코드에 정의된 스킬 ID 8종 — `slash2`(휘두르기)·`spin`(드래곤 트위스터)·`crushing`(딜레이 크러싱)·`slam`(와일드 스탬프)·`warcry`(블러드 레이지)·`power`(파워 스트라이크)·`destroy`(디스트로이 스윙)·`hell`(헬 파이어 소드) — 이며, 모션이 없는 패시브 3종(`mastery`·`body`·`instinct`)은 매핑에서 제외한다. 스킬을 추가할 때는 `skills.ts`에 ID를 넣는 것과 동시에 이 표에 템플릿을 지정하고, 4종으로 표현되지 않는 동작이 실측으로 확인될 때만 템플릿을 늘린다.

## 4. 본체 분리와 가림 규칙

초기 본체는 ① 머리 포함 몸통 ② 양팔 ③ 다리의 3영역으로 제작한다. 이 분리로 갑옷·투구·장갑·신발이 덮는 부위와 본체 노출 범위를 제어한다.

가림은 **파츠 가시성 숨김(visibility off)** 또는 **파츠 교체**(예: 투구를 착용하면 맨머리 파츠를 숨기고, 갑옷을 착용하면 맨몸 몸통 파츠를 갑옷 몸통 파츠로 교체)로 처리하며, **픽셀 알파 마스크는 사용하지 않는다**. 두 방식 모두 매니페스트의 파츠·슬롯 정의를 바꿔서 처리하고 런타임 픽셀 연산으로 가리지 않는다. 세 영역으로 해결할 수 없는 사례가 실제로 확인될 때만 별도 검토한다. 본체가 통짜인 상태에서 부위별 숨김이 가능한 것처럼 문서화하지 않는다.

## 5. 스켈레탈 도구 도입 판단

Spine을 1순위 검증 후보, 자체 PixiJS 레이어 조립을 비교 기준, DragonBones를 보조 조사 대상으로 둔다. 도입 여부는 아직 확정하지 않는다.

- Spine 공식 PixiJS v8 런타임은 @esotericsoftware/spine-pixi-v8이며 공식 문서는 PixiJS 8.16 이상을 요구한다. 현재 저장소 pnpm-lock.yaml은 PixiJS 8.23.0을 해석하므로 버전 조건상 검증 후보가 된다. Spine Editor와 런타임의 메이저·마이너 버전 일치도 확인한다.
- Spine은 본, 슬롯, 스킨 및 애니메이션 이벤트 등 이번 시스템 요구와 맞는 기능을 제공한다. 에디터 라이선스, 리깅 시간, 런타임 크기와 모바일 성능을 함께 평가한다.
- DragonBonesJS 저장소는 PixiJS 연동을 안내하지만, 현재 프로젝트 PixiJS 8 환경에서의 호환성을 별도로 증명해야 한다.
- 자체 구현은 PixiJS Sprite/Container와 최소 앵커 데이터로 시작할 수 있지만, 본·슬롯·스킨·애니메이션 편집 도구까지 직접 유지하는 비용을 평가한다.

**도입 판정 기준:** 같은 본체·무기·걷기 8프레임·갑옷 1종을 Spine 방식과 자체 레이어 방식으로 비교한다. 장비 교체, Z-order, 모션 재사용, 에셋 제작 시간, 런타임 용량, 렌더링 성능 및 라이선스를 기록한다. 비교 전에는 package.json, lockfile, PixiJS 버전을 변경하지 않는다.

**정량 기록 항목:** 도입 판정은 아래 수치를 같은 기기·같은 장면·같은 측정 절차로 비교해 표에 남긴다. 수치 없는 주관 평가만으로 도입을 확정하지 않는다.

| 항목 | 측정 방법 |
|---|---|
| 모바일 FPS | 대상 모바일 실기에서 대표 전투 장면(캐릭터 1기 + 몬스터 다수)을 재생한 평균·1% low — 최소 통과선은 60fps 유지 |
| 캐릭터 1기당 Draw Call | 캐릭터를 끈 상태와 켠 상태의 프레임당 draw call 차분(성별·동작별 최대값) |
| 런타임 번들 증가량 | 런타임 의존성 추가 전후 프로덕션 번들 크기(gzip, KB) |
| 런타임 메모리 증가량 | 텍스처·아틀라스 포함 GPU 메모리와 JS 힙 증가량(MB) |
| 라이선스 비용 | 에디터·런타임 라이선스 조건(고지 의무·매출 기준·팀 규모)과 실제 비용 |

이 수치를 기록하기 전에는 package.json, lockfile, PixiJS 버전을 변경하지 않는다(위 비교 전 제한과 같은 제약이다).

## 6. 아트 제작량과 에셋 규칙

### 6.1 제작량 계산

총 프레임 = attach 장비 수 × 1 + frames 장비별 고유 프레임 합계

frames 방식의 프레임 수에는 실제로 별도 그림이 필요한 성별 수 × 무기 계열 수 × 동작 템플릿 수만 곱한다. 동일 이미지를 재사용하는 조합은 중복 계산하지 않는다.

장비 100종 중 70종이 attach, 30종이 frames이고 기본 애니메이션이 13프레임이라고 가정한다.

| 가정 | 계산 | 총 프레임 |
|---|---:|---:|
| 공통 프레임 재사용 | 70 + 30 × 13 | 460 |
| frames 장비 남녀 분리 | 70 + 30 × 13 × 2 | 850 |
| 남녀 및 한 손 검/대검 분리 | 70 + 30 × 13 × 2 × 2 | 1,630 |
| 위 조건에 스킬 템플릿 17프레임 추가 | 70 + 30 × (13 + 17) × 2 × 2 | 3,670 |

이는 제작량 민감도를 보여주는 예시이지 실제 수량이 아니다. 갑옷 frames가 무기 계열별로 달라지는지 프로토타입에서 확인한 뒤 실 견적을 낸다.

### 6.2 프레임 및 아틀라스

- 본체 프레임 너비를 임의의 220px로 고정하지 않는다. 가장 큰 공격 동작과 무기 실루엣까지 포함해 캔버스 영역을 정한다.
- 같은 애니메이션 그룹은 일관된 캔버스와 발 피벗을 사용한다.
- 아틀라스는 장비 슬롯별로만 분할하지 않고 한 캐릭터가 함께 사용하는 리소스를 함께 묶는다.
- 2048×2048은 제작 목표, 4096×4096은 테스트할 상한 후보로 둔다. 실제 상한은 대상 모바일 기기의 GPU 한계와 메모리 측정 후 확정한다.
- 텍스처 번짐 방지를 위해 1~2px extrude를 검토한다.
- 아틀라스 수와 텍스처 전환량을 대표 필드 장면에서 프로파일링한다.
- **캐시 무효화:** `public/_headers`가 `/assets/*`를 `public, max-age=31536000, immutable`로 고정하므로, 같은 URL을 유지한 채 파일 내용만 바꾸면 기존 캐시가 계속 쓰인다. 신규 코스튬 아틀라스 PNG뿐 아니라 **매니페스트 JSON도** 버전 경로(`/assets/costume/v1/...`) 또는 `?v=N` 쿼리로 URL을 바꿔 무효화한다. 버전 값은 게임 코드의 한 상수에서 관리해 아틀라스와 매니페스트가 항상 같은 배포본을 가리키게 한다.

### 6.3 에셋 제작 주체

직접 제작·AI 생성·외주 중 한 방식으로 고정하지 않는다. 프로토타입은 하나의 일관된 제작 흐름으로 만들고 도구·버전·원본을 기록한다. 체형, 시점, 선화, 명암 및 프레임 일관성이 확보되지 않으면 프레임 수를 늘리기 전에 attach 또는 스켈레탈 방식의 적합성을 다시 검토한다.

## 7. 매니페스트 초기 범위

프로토타입 단계에서는 다음 항목만 사용한다. 실제 사례가 생기기 전에는 필드를 선제적으로 확장하지 않는다.

- schemaVersion: 매니페스트 구조 버전
- costumeId: 외형 고유 ID
- slot: 장착 부위
- animMode: attach 또는 frames
- anchor: 본체 기준점
- fit: 위치·크기·회전 보정
- zOrder: 기본 레이어 순서

방향·동작·프레임별 오버라이드, 성별 프로필, 색상·티어 변형, 가림 세부 필드는 프로토타입에서 필요성이 확인된 뒤 추가한다.

## 8. 성능·범위·안전장치

- 신규 시스템은 초기에는 플레이어 1명에만 적용한다. 몬스터와 NPC 렌더링은 변경하지 않는다.
- 성능 문제는 실제 기기와 대표 전투 장면에서 측정한다. 장비 조합 런타임 베이킹은 레이어 렌더링이 병목으로 확인된 경우의 대안이다.
- 장비 외형 로딩에 실패하면 기본 외형으로 폴백해 본체가 사라지지 않도록 한다.
- 캐시 무효화: `/assets/*`의 `immutable` 정책 때문에 기존 URL을 유지한 채 내용만 바꾼 에셋은 갱신되지 않는다. 코스튬 아틀라스 PNG와 매니페스트 JSON은 배포마다 버전 경로 또는 `?v=N`을 올려 참조를 바꾼다(§6.2). 매니페스트와 아틀라스의 버전이 어긋나면 폴백으로 처리하고 콘솔에 남긴다.
- 미사용 에셋은 목록만 보고하고 자동 삭제하지 않는다.
- 기존 리소스 삭제는 신규 시스템 전환과 전체 참조 검사 이후 별도 PR에서 한다.
- Save/DB/API와 전투 로직 변경은 코스튬 작업에서 분리하고 사전 승인받는다.

## 9. 프로토타입 완료 기준

1. 본체 3영역이 실제 이미지로 자연스럽게 연결된다.
2. 본체 1종과 무기 1종의 걷기 8프레임에서 앵커가 안정적으로 유지된다.
3. 한 손 검과 대검의 본체 공격 자세 차이를 표현한다.
4. 같은 갑옷을 두 무기 계열에 적용해 프레임 재사용 가능 여부를 판단한다.
5. 투구와 망토의 부착·가림·Z-order를 확인한다.
6. 베기·회전·내려찍기·발동 자세 템플릿의 장비·이펙트 동기화를 확인한다.
7. Spine과 자체 구현 중 하나를 근거와 함께 선택한다.
8. 실제 제작량과 모바일 성능 측정 결과를 기록한다.
